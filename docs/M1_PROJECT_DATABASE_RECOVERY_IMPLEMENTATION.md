## Coverage and fault interpretation

Real SQLite cases include empty/populated stores, two owners, duplicate names, immutable referenced and unreferenced PNGs, committed revisions, scene locks/actors, exact row/BLOB comparisons, normal storage-module reopen, restart and foreign-owner refusal. DELETE and WAL campaigns keep a source writer open, verify pending WAL frames, force more than one backup batch, commit asset import plus scene save during progress and prove the snapshot is a coherent committed state with its matching PNG reference. A rolled-back write is excluded. A killed uncommitted transaction tests hot-journal refusal followed by normal SQLite recovery in the disposable fixture.

Invalid-package cases include missing/bad/future manifest, count mismatch, changed bytes, truncated SQLite, corrupt B-tree, future version, missing tables/index, extra trigger, FK violations, corrupt scene/revision/owner, foreign/missing asset reference, digest/dimensions/PNG corruption, unexpected package file, symlink and hardlink aliases. Each compares the rejected backup inventory and absent destination, then confirms an existing sentinel destination remains unchanged. Account recreation and unsafe/public/sidecar/directory destinations have explicit refusal checks.

Fault injection includes snapshot creation/write, manifest creation/write, final backup destination creation, restore staging, SQLite validation, final restore publication, tampered staging and concurrent destination creation. Tests examine directory entries and committed source/target rows. Unknown replaced objects are intentionally retained; cleanup is restricted to held, owned inodes. SIGKILL before manifest creation leaves a private incomplete stage and no completed backup; a separately killed SQLite transaction verifies source commit preservation. Exceptions and filesystem/process interruptions are distinct from untested power failure. ENOSPC, hardware faults, actual fsync-failure durability and network filesystem behavior are NOT_TESTED; no claim follows merely from ordinary injected exceptions.

The real host campaign reuses the existing storage/portability checkpoints and adds online backup while the source host runs, exact snapshot row/hash verification, stopping it, explicitly provisioning a fresh disposable target's synthetic native/account files without its SillyNovel DB, read-only account verification, empty-slot restore, normal host startup, every project and asset readback, two-account separation, explicit browser reopen, rendered background/two sprites, native reader/composer/draft, restart and native-file inventory comparison. Only named inventoried files receive a non-mutation claim.
