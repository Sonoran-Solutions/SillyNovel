## Executive decision summary

### Recommendation — PROPOSED

Choose **Option A: a small, versioned upstream SillyTavern host API** as the only preferred path to production persistence. SillyTavern must own stable user/store, character/group, chat, visit, source-revision, and write-generation identity; route every supported native writer through the same lifecycle/CAS boundary; store extension visual records and immutable assets outside canonical chats/cards; and provide coherent backup plus explicit bundle export/import. SillyNovel should contain only a small client adapter and visual semantics.

Use **Option D: visibly session-only visuals** as the fallback and acceptable interim distribution. If the host capability is absent, incompatible, or unavailable, the normal text reader/chat remains usable and all visual state is explicitly unsaved. It does not meet reloadable-scene acceptance and does not unblock DYL-22 or DYL-23.

Do not select a required server plugin or separate service. Current official SillyTavern guidance says server plugins are opt-in and unsandboxed, and UI extensions that require one will not be accepted. A separate service adds credentials, operations, privacy and restore complexity while leaving native chat correspondence unresolved. These conclusions were checked against the [current server-plugin guide](https://docs.sillytavern.app/for-contributors/server-plugins/) and [UI-extension submission guide](https://docs.sillytavern.app/for-contributors/writing-extensions/) on 2026-10-15.

**Decision disposition: GO for owner review of this architecture direction; NO-GO for production persistence today.** DYL-46 is a GO for bounded experimental feasibility under the latest owner-approved experimental contracts. It is not a supported host API, production approval, Gate A verdict, or evidence that unknown writers are safe. Unknown/unobserved writers remain outside the guarantees. The owner must choose the deployment, recovery, backup, asset and release defaults below. Only after that decision may the team prepare an upstream proposal; submitting it requires separate approval.

### DYL-25 comparison with current evidence

DYL-25 correctly identified the best ownership location and fallback. This checkpoint retains that recommendation but adds three constraints: (1) storage alone is insufficient without host-enforced writer participation and lifecycle identity; (2) independent rollback authority and its backup boundary are product operations that need explicit recovery ownership; and (3) the experimental protocol's whole-store refusal, synchronous witness, per-read validation and filesystem layout are evidence mechanisms, not a production API blueprint. A production API may use a different internal design if it preserves the invariants in section 3 and makes failures recoverable by an explicit supported procedure.

The current official UI-extension docs describe extension settings, current chat metadata saving and character-card fields, but these do not meet this contract: chat metadata is saved for the current chat, while the docs identify `characterId` as an array index, not a durable identity. Current official docs also say UI extensions must track latest SillyTavern changes. Current server-plugin docs specify the opt-in `enableServerPlugins` setting and warn plugins are unsandboxed. These published surfaces are real, but none is a supported targeted extension store with durable identities, native writer participation and rollback-safe recovery. References: [UI extensions and state management](https://docs.sillytavern.app/for-contributors/writing-extensions/#state-management), [server plugins](https://docs.sillytavern.app/for-contributors/server-plugins/).

## 3. Minimum production host contract

The host should expose a small, versioned, capability-negotiated extension service for namespace `sillynovel`. It need not expose DYL-46's file layout, locks or witness format. It must preserve these outcomes. The host authenticates the account from its request context; client/model input never selects filesystem paths or account ownership.

## 4. Supported writer boundary and trust assumptions

The minimum realistic enforcement is a host-owned canonical mutation service used by all UI/API operations that can change a relevant chat, character/group identity, membership or account scope. At that boundary the host allocates identity, advances source/write generations, reserves the store operation, invalidates obsolete visits, commits canonical changes, and finalizes extension-state authority. Transaction identifiers and responses must correspond to actual host mutations; an extension event emitted after the fact is insufficient to prevent stale writes.

The current DYL-42/43 inventories include native chat save/import/rename/delete, character create/rename/delete/avatar/import, group mutations, bookmark/branch/copy paths, JSON converters, Data Maid, startup group migrations, account reset and legacy moves. Some entries are source-inspected only; some bypass the shared chat writer or perform multiple writes. A production support claim requires exhaustive maintained inventory plus regression coverage for each supported route—not just the campaign counts.

Host filesystem permissions can prevent ordinary plugins/processes from writing canonical data only if the host actually controls those capabilities. In the default extensible local Node environment, a server plugin runs unsandboxed with process privileges. Therefore no absolute guarantee against a trusted operator or arbitrary same-user filesystem process is realistic. The initial supported boundary should be: supported SillyTavern native writers and approved in-process code go through the host service; third-party plugin or external filesystem mutations are unsupported; if detected, persistent visuals are disabled pending explicit recovery. Hashing, inode metadata, watcher events and polling can detect some changes but cannot prove an unobserved same-byte restore never happened.

**PROPOSED initial assumptions:** one host installation and one authenticated account; one active supported SillyTavern process; character chats only; local host backup is coordinated; unsupported plugins/filesystem writers do not mutate protected canonical or visual data; no cross-device sync; groups, Temporary Chat persistence and account deletion/recreation are refused until explicitly covered. The native chat must remain readable/replyable if visual identity/storage fails, except a host mutation whose partial canonical outcome itself is unsafe; that writer may need to refuse until an administrator restores consistency.

## 5. Recovery, availability and backup policy — PROPOSED

Availability follows the experimental distinction: a failure of visual storage alone disables persistent visuals while ordinary reading/replying continues; a native writer may be refused only when proceeding could corrupt canonical chat or make its own transaction outcome unknowable. Do not make permanent whole-store refusal a normal result. Provide a documented administrator recovery transaction before release; do not silently clear pending authority, adopt files by name, or recreate old identity from chat contents.

| State | Recommended response | User-visible consequence |
|---|---|---|
| Verified clean abort (pre-write validation proves no canonical mutation) | Host may finalize forward at a new generation using durable proof; no rollback to old generation | Native operation reports its original failure; prior visual record may remain usable if host proves exact unchanged scope/revision |
| Completed scope/chat revocation | Keep revoked identity permanently disabled; healthy unrelated scopes may continue after verified transition | Affected chat uses native text; user/admin may explicitly rebind as a fresh identity only through supported workflow |
| Partial canonical mutation | Mark indeterminate; require explicit admin restore/migration transaction; never infer commit/abort from matching bytes alone | Affected persistent visuals disabled; refuse only native operations that could compound corruption; reading remains available where host can safely read |
| Interrupted reservation | Durable pending/receipt state remains; automatic timeout/restart clear forbidden; admin recovery inspects canonical state and commits a new forward transition | Visuals disabled for affected store/scope; normal chat access retained unless a native writer needs the locked transaction boundary |
| Failed external finalization | Treat as indeterminate even if native write returned success; query durable operation receipt or require explicit recovery; never report visual commit | Native chat may contain the completed write; visuals remain disabled until reconciliation |
| Interrupted validation witness | Missing/pending/corrupt witness never initialized from current files; admin recovery from a trusted snapshot or explicit fresh enrollment | Persistent visuals unavailable; native transcript can be read if host can validate ordinary file access |
| Missing/corrupt local registry | Do not rebuild from names, JSONL or embedded metadata; use verified host backup/migration or create fresh identities after owner/admin action | Text remains; all affected stored scenes unavailable until reviewed recovery |
| Missing/corrupt external authority | Refuse persistence; restore only through an authenticated host restore transaction that validates both authorities and advances incarnation | Text remains available; persistent visuals disabled; no silent bootstrap |
| User-root rollback | Detect mismatch against authority; do not roll authority backward; restore user data forward to the authority's known generation or perform explicit fresh-store migration | Visuals disabled during recovery; text from restored data may be readable; stale scene records never reappear automatically |
| Full host restore | Restore canonical files, extension records/assets and authority through one host-coordinated consistent backup/restore transaction; otherwise treat as incomplete | On partial restore, text may remain readable, but visuals disabled and unsafe native writes may be refused pending admin action |
| Account deletion/recreation | Host revokes old account incarnation; new account receives new store identity; no same-handle reattachment or auto-enrollment | Old visual state is unavailable; imported bundle can be manually validated into new IDs if allowed |
| Unknown filesystem/plugin writer | Out of support; host access control is the preferred prevention. If host observes evidence, revoke affected scope and require explicit recovery; no watcher/hash claim of completeness | Native chat remains accessible where safe; persistent visuals are unavailable for affected scope |

### Backup ownership and restore

**PROPOSED owner:** SillyTavern host/operator owns a consistent backup containing (a) canonical user/chat/card files, (b) the SillyNovel namespace records, immutable asset bytes and references, and (c) account/store-incarnation and transaction/authority metadata. That backup set is captured/restored atomically or with a signed/versioned manifest that validates one consistent generation. The separately trusted monotonic authority must not be rewound independently of the user root; conversely, restoring the root without matching authority is incomplete and must refuse persistent visuals. SillyNovel owns schema/version validation and a user-readable export bundle, not host filesystem recovery. The user/operator chooses and stores backups; release docs must say so and describe restore failure behavior.

Initial support proposal: same-host coordinated backup/restore only; no cloud sync or cross-device identity continuity. Portable user-invoked export/import remains required before claiming portability. If it cannot ship in the first persistence slice, label that slice same-host only and keep bundle work as an explicit release blocker/owner-approved deferral; never claim ordinary SillyTavern chat export includes visual state.

## 6. Security, privacy and maintenance risks

- **Account and scope mix-up:** usernames, display names, character indices, filenames, avatars and embedded imported IDs are not authority. Host-resolved opaque identities and authenticated request ownership are required.
- **Stale/rollback writes:** a successful HTTP response is not a durable acknowledgement; source revision, writer generation and visual-record revision are separate counters. CAS checks must occur in the same host transaction as the mutation.
- **Untrusted imports and model output:** imported bundle fields cannot set host IDs, paths, URLs, scripts, commands or account identity. Chat/model content stays untrusted prose. Never put visual machine tags into ordinary roleplay text or prompt.
- **Plugin privilege:** official docs describe server plugins as unsandboxed. Requiring one expands supply-chain, filesystem and update risk and violates current official UI-extension submission guidance.
- **Independent authority operations:** an independently stored rollback witness increases backup, migration and support complexity. The host/operator must own the consistency transaction and documented admin recovery. The experiment's separate directory is not a production security boundary against the same OS principal.
- **Assets:** raster decode, format, dimensions, file and total quotas, immutable revisions, digest verification, reference-safe removal, and archive bomb/path checks require implementation and tests. Asset names are labels, not paths or identities.
- **Availability and maintenance:** conservative refusal protects canonical text/visual correspondence but can disable visuals after crashes or incomplete restores. A product release needs a supported admin recovery operation and tested user guidance, not indefinite store lockout.
- **Host compatibility:** current docs require extensions to work with the latest host release. Internal imports/endpoints can change. Only a documented, versioned capability with capability discovery and a tested fallback is suitable for durable production support.

## 7. Initial host compatibility policy — PROPOSED

Set the minimum supported SillyTavern release to the first upstream release that ships and documents the accepted capability version and passes the extension's pinned integration suite. The exact version is **not yet knowable** and must not be inferred from the 1.19.0 experimental host. At startup, SillyNovel checks capability version and required semantics; if absent or incompatible, it exposes session-only state (or hides persistent controls) and tells the user visuals are unsaved. Native reading, chat and reply stay available. Do not fall back to chat metadata, extension settings, localStorage, a plugin or a service without a separate proposal and approval.

Track the latest SillyTavern release as official extension guidance requires. Keep a small compatibility matrix of exact host release/commit and API versions. A host release that removes or weakens required guarantees becomes unsupported for persistence until revalidated; session-only mode remains the downgrade path. Do not promise groups, multiple host processes, shared accounts, networked remote clients or cross-device sync in version one.
