## File contract

A `.sillynovel` file is a user-controlled **copy of one saved independent visual project**, not a conversation backup or database restore. Version 1 is UTF-8 canonical JSON (`JSON.stringify` without whitespace/BOM/trailing newline), with exactly these fields:

```text
{
  format: "sillynovel-project",
  version: 1,
  name: bounded project display name,
  scene: existing project-global schema v1,
  assets: [{assetId, mediaType: "image/png", byteLength, sha256, data}]
}
```

`data` is canonical padded base64 of the exact PNG bytes; `sha256` is lowercase 64-digit SHA-256. `byteLength` is the decoded encoded-file length (not pixel memory). `assetId` is a UUID v4 local reference within the bundle. Each referenced PNG appears exactly once, including assets shared by background/actors. Asset arrays contain neither duplicates nor unreferenced entries. All scene asset references must resolve within that file; existing database IDs never satisfy a missing declaration. Source asset and actor UUIDs have no ownership authority.

Scene fields are exactly `backgroundAssetId`, `backgroundLocked`, `actors`. Each actor has exactly `actorId`, `name`, `spriteAssetId`, `slot`, `present`, `locks`; locks have exactly `presence`, `slot`, `outfit`. Up to 20 unique actor UUIDs and three unique occupied slots (`left`, `center`, `right`); nullable assets/slots and explicit absence/locks survive. Existing schema validation is shared rather than duplicated.

No source project ID/revision, account authority, native chat IDs/filenames/paths, transcripts, auth data, database paths, expressions/history, scripts, URLs or filesystem entry types exist in the format. Extra fields anywhere are refused. Labels remain inert text, never evaluated. No bundle content is fetched, executed or extracted to disk. Importing into another authenticated account creates its own independent copy; a bundle is intentionally portable and should be shared only deliberately.

## Container choice and resource bounds

Engineering choice for this experimental slice, **not an owner-approved final production policy**: use the standard JavaScript JSON parser and Node Buffer base64 codec, rather than ZIP. PNG already compresses image data; ZIP offers little benefit here while adding a dependency and central/local-header, path, symlink and expansion ambiguities. No custom archive parser or dependency was added. ZIP and all other compression/container methods are refused, even if their filenames end in `.sillynovel`. There are no entry names or paths: only validated UUIDs. Absolute/traversal identifiers, special entry fields, duplicate asset IDs and arbitrary executable entries fail closed.

Canonical serialization equality additionally refuses duplicate JSON keys, invalid UTF-8, alternate encodings, trailing content and hand-formatted JSON. Object key order is not separately fixed: the input must equal its parsed object's JSON serialization. Files generated by v1 round-trip; this is intentionally not a general JSON/ZIP importer. Unsupported versions and unexpected keys refuse the entire file. A future interoperability format needs its own reviewed contract.

| Resource | Experimental v1 ceiling |
|---|---|
| HTTP/file body | 8 MiB + 32 KiB (8,421,376 bytes) |
| Total encoded PNG bytes after base64 decoding | 6 MiB |
| PNG entries | 21 (background plus 20 actors) |
| Scene/name JSON | 32 KiB |
| Each PNG | Existing 5 MiB, 4096px edge, 16M pixel validation ceiling |
| Aggregate decoded pixels per bundle | 4,194,304 pixels (16 MiB RGBA) |
| Bundle processing | One operation per plugin process; concurrent requests receive 429 BUNDLE_BUSY |
| Worker | 128 MiB old-generation V8 limit; 15-second timeout |
| Account quotas | Existing 100 projects, 100 MiB encoded PNG bytes; no automatic cleanup |

The aggregate pixel limit is deliberately smaller than the existing individual-upload limit. Oversized export **refuses the entire project**; it never drops artwork. Existing projects above this ceiling remain readable/saveable. Base64 creates roughly 4/3 expansion. JSON parsing/serialization, SHA-256 and all imported/exported PNG decoding run in a worker thread; full decoding is sequential and aggregate pixel/byte bounds are checked first. The existing PNG contract verifies signature, chunks, no APNG, bounded inflate, CRC and full pngjs 7.0.0 decode. No new npm dependency; SQLite remains built-in `node:sqlite`, runtime floor Node >=22.13. Worker heap limits do not cap external Buffers or total process RSS; measured resource evidence and limitations belong in the implementation report.

The router admits one body/worker operation at a time; body collection is streaming-capped before parsing, and compressed HTTP bodies are refused. Buffer copies, base64 strings, canonical serialization and SQLite pages consume additional bounded memory. A host/global parser can still consume requests deliberately mislabeled as application/json before plugin rejection; reverse-proxy/rate/slow-client policy remains operator work inherited from the plugin. No temporary bundle files are written by the server.

## API and transactions

Same authenticated account and CSRF boundary as the optional plugin. Ownership comes solely from host session `(handle, created)`; accounts-disabled and CSRF-disabled configurations still refuse persistence. Every lookup checks owned project identity. Foreign/unknown export IDs receive 404 without filesystem paths. Public error bodies contain codes, never stacks or native paths.

- `GET /api/plugins/sillynovel-storage/projects/:id/export`: validate UUID and ownership; read saved scene and only its referenced immutable asset rows in one `BEGIN IMMEDIATE` transaction, with byte ceiling before copying each BLOB. Verify stored digests. Release the short snapshot transaction before worker validation/serialization. A racing save produces a coherent committed snapshot; export never increments the revision. Return `application/vnd.sillynovel.bundle`, attachment filename `project.sillynovel`, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, sandbox/default-none CSP. Corruption/limits refuse before any download.
- `POST /api/plugins/sillynovel-storage/projects/import`: exact bundle media type; validate entire container/schema/references/base64/hashes/PNGs in the worker **before** opening a write transaction. Then `BEGIN IMMEDIATE`, recheck project and byte quotas, allocate fresh random project/actor/asset UUIDs, insert project and immutable assets, remap every scene reference, insert final scene, load result, COMMIT. Response 201 contains the new project at revision 0. Duplicate display names are permitted. Existing projects are never updated. Any insertion/finalization/commit error rolls everything back. No returned HTTP failure alone counts as rollback evidence: tests inspect committed tables.

The temporary empty scene needed for the foreign-key parent row is inside the same transaction and never observable by another connection. No cancellation-based rollback promise after successful commit: if a response is lost, the new project can exist and appears in a later list. Retrying intentionally creates another independent copy; concurrent callers may need an explicit retry after 429. No idempotency/deduplication policy is inferred.

## Browser behavior and delayed responses

Explicit **Export project** exports the saved-list selection, including saved state only; dirty current edits remain untouched. Explicit **Import project bundle** opens a local file control with extension/size checks, then server validation. Successful import refreshes the list while retaining its prior selection and displays the imported name and UUID, says it is not attached, and directs the user to select it and choose **Open project and use with this chat**. It never installs an imported model, clears dirty state or invokes native chat association.

Import/export capture model identity, project replacement epoch and native session epoch; delayed receipts after replacement/chat switch cannot update current controls or install actors/art. Selecting another saved entry remains possible and refreshed options preserve that selection. Native composer/reader remain usable. Existing replacement/PNG-import gates still apply. Missing or older plugins disable bundle controls while preserving session-only visuals. Failure reports an explicit error without an empty download or stage mutation.

## Database recovery is separate

Portable imports discard source authority and allocate new IDs. Whole-database restore may need old IDs/revisions, schema/account reconciliation, coordinated live connections, consistent journal/WAL handling and a validated target. Never overwrite a running store. No arbitrary SQLite upload, restore endpoint or client filesystem destination exists here. DYL-58 must define and verify those policies before recovery can be advertised. DYL-59 must handle ownership and concurrent save/import/deletion before cleanup is implemented. Retain existing database/journals and follow the plugin's refusal behavior; portable bundles alone do not provide administrative disaster recovery.
